SECTION A — SCIENTIFIC CORRECTIONS
================================================================================

A1. [SCIENCE] Over-strong claim about Hamming weight and dimension
    Issue     : The report asserted categorically that increasing the lattice
                dimension at a fixed Hamming weight of two does not increase
                cryptographic difficulty. That is false as stated: the candidate
                space C(n,2) = n(n-1)/2 does grow with n.
    Original  : Abstract — "...exhaustive enumeration ... would succeed at every
                dimension considered, without any neural network."
                Section 8.3 — "increasing n while holding h = 2 does not
                increase the cryptographic difficulty of the instance."
                Section 6.8 and Chapter 9 carried the same assertion.
    Change    : Rewritten in all four places. The report now states that the
                candidate space grows QUADRATICALLY with n (66 at n = 12, 190 at
                n = 20, 435 at n = 30, 8,128 at n = 128), that this is growth in
                the right direction but small in absolute terms across the
                tested range, and that exhaustive enumeration therefore remains
                a CREDIBLE COMPETING BASELINE rather than a guaranteed success.
                A new numbered equation (8.1) states C(n,2) explicitly.
    Reason    : Accuracy. The original wording confused "does not grow" with
                "does not grow fast enough to matter".

A2. [SCIENCE] Unqualified cost claim for the enumeration baseline
    Issue     : The enumeration baseline was presented as obviously practical,
                with no statement of what had not been measured.
    Change    : Section 8.3 now gives the cost explicitly — O(mn) per candidate,
                about 2.1e9 multiply-accumulate operations at n = 128 with
                m = 2,048 — and then states two qualifications that the project
                has NOT measured: (i) the four acceptance criteria of Section
                3.6 were calibrated for a single candidate and their
                false-acceptance rate over thousands of candidates is unknown,
                and no tie-breaking rule exists in the implementation; (ii) the
                24-fold verifier separation was measured only at n = 12 and
                n = 20.
    Reason    : A baseline claim must carry its own uncertainty.

A3. [SCIENCE] New future-work item added
    Change    : Table 8.1 gained a row: "How reliable is the verifier over many
                candidates?" — measure the false-acceptance rate of the four
                criteria across a full C(n,2) enumeration, cost minutes of CPU
                time.
    Reason    : A2 identifies an unmeasured quantity; the work plan should name
                the experiment that settles it.

A4. [SCIENCE] Replay runtime made exact
    Issue     : "replays ... in approximately one second" was an approximation
                where the artefact holds exact values.
    Original  : Section 5.4, Appendix C.1, Section 6.8 — "about one second".
    Change    : Now 1.19 s at n = 12 and 1.59 s at n = 20, from
                results/final_pipeline/pipeline_report.json
                (runtime_seconds 1.1944 and 1.5947).
    Reason    : The exact figure was available and is more useful.

A5. [SCIENCE] Replay agreement described specifically
    Original  : "Replay agreement: 12/12 checks."
    Change    : Section 5.4 now names the six quantities re-derived per
                dimension — exact recovery, coordinate accuracy, Hamming
                distance, count of successful multipliers, verification outcome
                and parameter count — which is what the artefact records.
    Reason    : "12 checks" alone does not tell the reader what was checked.

A6. [EDIT] Softened an unverifiable process claim
    Original  : Declaration — "All software described in this report was written
                from first principles during the internship."
    Change    : "All software described in this report was written during the
                internship." The sentence about the original SALSA code being
                consulted as reference material and not copied is retained.
    Reason    : "From first principles" is a claim about process that the
                artefacts cannot evidence; the substantive claim (no code
                copied) is retained and is supported by the fidelity audit.

A7. [EDIT] Scalability wording aligned with the required distinction
    Original  : Section 7.2 — "input-shape compatibility is not learned
                capability".
    Change    : "technical compatibility with a dimension is not demonstrated
                secret-recovery capability at that dimension".
    Reason    : States the intended distinction unambiguously.

A8. [EDIT] Forecast curves labelled on the figure note
    Change    : The note under Figure 7.1 now ends: "The dashed and dotted
                curves are forecasts, not measurements."
    Reason    : The figure mixes one measured series with two predicted ones.

A9. [EDIT] Citation added for a tool already in use
    Issue     : AdamW appeared in the configuration tables and in the reference
                list as [15], but was never cited in the text.
    Change    : Section 2.2 now ends "The optimiser used throughout is AdamW
                [15]."
    Reason    : Every reference should be cited at the point it is used.

A10. [EDIT] Symbol list completed
    Change    : Added m (number of samples) and C(n,h) (binomial coefficient) to
                the list of principal symbols; both are used in the text.

SECTION D — FORMATTING AND LAYOUT
================================================================================

D1. [FORMAT] Page geometry
    A4 throughout. Margins 25 mm top, 22 mm right, 20 mm bottom, 32 mm left; the
    wider left margin is a binding allowance. The cover uses 18/20/18/20 mm.

D2. [FORMAT] Typography
    Body Times New Roman 12 pt, line spacing 1.5, justified, hyphenated, with
    orphan and widow control set to 3 lines. Chapter headings 16 pt bold with a
    rule beneath and a small-capital chapter label above; section headings
    13 pt bold; subsection headings 12 pt bold. Headings are black, not Word's
    default blue, and are kept with the text that follows them.

D3. [FORMAT] Page-break control
    Every chapter starts on a new page. Headings cannot be stranded at the foot
    of a page. Tables, table rows, figures and equations do not split across
    pages. Captions and their explanatory notes are kept with the object they
    describe.

D4. [FORMAT] Tables
    Header rows are marked up as <thead> so Word and any print renderer repeat
    them when a table spans pages. Numeric columns are right-aligned, text
    columns left-aligned, borders consistent at 0.6 pt. Font reduced to 9.5 pt
    (9 pt for the three widest tables) so that no table overflows the text
    width. Table captions sit above their tables; figure captions sit below
    their figures, matching the reference report.

D5. [FORMAT] Figures
    All six are centred, constrained to the printable width, and rendered at
    200-220 dpi so they remain sharp at normal PDF zoom. Source resolutions are
    1609x889 to 2089x1028 px.

D6. [FORMAT] Equations
    Centred on their own lines, numbered (3.1)-(3.10), (4.1), (7.1) and the new
    (8.1), with the number set flush right and every equation referenced in the
    text.

D7. [FORMAT] Captions and notes
    Caption labels are bold ("Figure 4.1:", "Table 6.1:"). The "what this shows
    / what this does not establish" paragraph under each figure and table is
    rendered as an indented note with a grey left rule, so it reads as commentary
    rather than body text.

D8. [FORMAT] Page numbering
    Continuous arabic throughout, centred in the bottom margin, with the cover
    page left unnumbered. Verified in the rendered PDF: the footer strip of
    page 1 contains no marks, pages 9 and 25 carry their numbers.
    Roman front matter was attempted first and withdrawn. Chrome honours the
    @page margin boxes and named pages in the stylesheet, so lower-roman front
    matter rendered correctly, but it does not honour a mid-document
    "counter-reset: page", so the body continued from xiii to 14 instead of
    restarting at 1. A single consistent scheme was judged better than a
    half-working two-part one. If you want roman front matter with the body
    restarting at 1, build the DOCX (Section G) — Word does this with real
    section breaks.

D9. [FORMAT] Document metadata
    Title, author (Nandini Shukla), subject (research internship report,
    Scientific Analysis Group, DRDO) and keywords are set in the HTML head and
    carried into the PDF.

SECTION G — HOW THE PDF WAS PRODUCED
================================================================================

The PDF is rendered from the finalised HTML by headless Google Chrome, driven
through the DevTools Protocol (Page.printToPDF with preferCSSPageSize), so the
page size and margins come from the document's own @page rule rather than from
a browser default. This is a true document export: the text is selectable, the
six figures and the DRDO logo are embedded images, and the fonts are embedded
as subsets. It is not a screenshot.

Verified on the delivered file:
    58 pages
    MediaBox 594.96 x 841.92 pt = 209.9 x 297.0 mm (A4)
    8 embedded images
    6 embedded font subsets (Times New Roman roman/bold/italic/bold-italic,
      Cambria Math for the mathematical symbols, Consolas for code)
    tagged PDF, valid %%EOF
Pages 1, 2, 9, 22, 25, 31 and 46 were rasterised and inspected by eye. Cover
layout, certificate, the contents lists, a chapter opening, a full-page figure
with its caption and note, and a wide table that splits across a page boundary
with its header row correctly repeated were all checked. No clipping, no
overlap, no overflow, no stranded heading and no unintended blank page was
found.

Two earlier routes were tried and rejected:

  Paged.js (the CSS Paged Media polyfill) was the first choice, because it
  would have supplied target-counter() page numbers inside the three contents
  lists. It stalled after laying out two pages of this document and never
  signalled completion, under virtual-time budgets up to 600 seconds and with
  named pages and heading page-breaks removed as tests. Rejected rather than
  shipped truncated. report_final/build_pdf.ps1 keeps that attempt for the
  record; it runs but its output is incomplete.

  Microsoft Word via COM automation produces a 62-page document with live
  TOC/LoF/LoT fields carrying real page numbers, a genuine section break and
  roman-to-arabic numbering, plus a DOCX. It works — it reached "Repaginated:
  62 pages" and updated all three lists — but a single save of a document this
  size takes roughly ten minutes headless, and the run was interrupted twice.
  It remains available: run report_final/build_docx_pdf.ps1 and allow about
  fifteen minutes. Use it if you want the DOCX or printed page numbers in the
  contents lists.

No third-party PDF library (reportlab, WeasyPrint, wkhtmltopdf, Pandoc,
LibreOffice, LaTeX) is installed in this environment; none was installed.

To regenerate:
    python report/make_figures.py
    powershell -ExecutionPolicy Bypass -File report_final/build_pdf_chromium.ps1
    powershell -ExecutionPolicy Bypass -File report_final/preview_pdf_pages.ps1 -Pages "1,9,25,46"

The third command rasterises chosen pages to PNG using the Windows PDF
renderer, for checking the layout by eye.
